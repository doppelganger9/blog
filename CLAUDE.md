# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

David Lacourt's personal blog (https://lacourt.dev), a fully prerendered SvelteKit 3 / Svelte 5 static site. Posts are Markdown compiled by mdsvex. Deployed to Netlify, which also hosts the serverless functions in `lambda/`.

## Commands

```bash
npm install          # postinstall runs svelte-kit sync, applies patches/ via patch-package, and installs lambda/ deps
npm run dev          # Vite dev server on http://localhost:3000
npm run build        # static build into build/ (adapter-static)
npm run check        # svelte-check type checking
npm test             # Playwright e2e tests against build/ (served on :8080 by the webServer of playwright.config.ts) — run `npm run build` first
npm run test:coverage # same, with V8 code coverage mapped to src/ via the sourcemaps: coverage/lcov.info + coverage/index.html
npm run test:ui      # Playwright UI mode
npx playwright test e2e/home.spec.ts   # single spec
npm run start:lambda # serve Netlify functions locally (netlify-cli, port 9999)
```

CI (`.github/workflows/nodejs.yml`, Node 24) runs `npm ci`, installs Playwright's Chromium, `npm run build` and `npm run test:coverage` on every push (and, in a parallel `visual` job, the visual regression tests), uploads `coverage/lcov.info` to Coveralls and the Playwright report as an artifact on failure. There are no unit tests or linter; Playwright e2e against the built site is the test suite. Coverage is Chromium's V8 coverage of the production build (no instrumentation), collected per test by the auto fixture in `e2e/fixtures.ts` and merged by monocart-coverage-reports (`e2e/coverage-*.ts`).

A weekly workflow (`.github/workflows/links.yml`, config in `lychee.toml`) checks the links of `src/posts/*.md` with lychee (root-relative ones against the live site) and keeps a single issue labelled `broken-links` up to date (opened or updated when links break, closed when they all work again); it also runs, without touching issues, on pushes that change the workflow or its config. Add an `exclude` there for sites that block bots.

## Architecture

**Posts pipeline.** `src/posts/*.md` (or `.svx`) are mdsvex modules: `default` is the rendered Svelte component, `metadata` the frontmatter. `src/lib/post.js` turns a path + metadata into the post view model (slug, dates, minutes to read, categories, tags). `src/lib/posts.js` imports every post eagerly with `import.meta.glob` and builds the `POSTS` list (newest first): it is **server-side only** (home page `+page.server.js`, RSS feed `src/routes/rss`, sitemap, `hooks.server.js`), never import it from client code or every visitor downloads all the posts. Post pages (`+page.js` of `[year]/[month]/[day]`, `[slug]`, `future/[slug]`, `alternate-reality/[slug]`) use `src/lib/postPage.js`, which imports only the requested post (lazy glob, one chunk per post) through `virtual:post-index`, a `{ slug: file }` map generated by the `postIndex` plugin in `vite.config.js` from the `slug` frontmatter field; `posts.js` fails the build if that map disagrees with mdsvex. Post pages keep universal loads on purpose: a `+page.server.js` on a route with parameters makes adapter-static write `2019/05/20/__data.json` next to `2019/05/20.html`, and the directory shadows the page on static servers.

**Frontmatter matters for routing.** The `slug` frontmatter field overrides the filename-derived slug and determines the URL:
- Dated posts use `slug: YYYY/MM/DD` → served by `src/routes/[year]/[month]/[day]`. The filename date is not used for routing.
- `slug: future/<name>` and `slug: alternate-reality/<name>` are hidden posts (files named `FUTURE-*` / `ALTERNATE-*`) served by their own routes and excluded from listings.
- Only `published: true` posts appear on the home page/RSS (`getPublishedPosts`). Unpublished dated or `[slug]` posts are also a 404 in the production build (`loadPublishedPostForSlug`), so a published post linking to a draft fails the prerender; drafts stay visible with `npm run dev`. `future/` and `alternate-reality/` teaser pages are intentionally unpublished and still built.
- Other fields: `title`, `date`, `description`, `lang` (`en` default or `fr`; affects date formatting and reading time), `category` and `tags` (comma-separated strings), `keywords`, `thumb`.

**mdsvex config** (`mdsvex.config.js`) adds remark/rehype plugins: a custom plugin that injects `wordCount` into frontmatter (used for minutes-to-read), oEmbed embeds, abbreviations, twemoji, PlantUML (rendered via plantuml.com), figures, heading slugs/anchors, and external links opened in a new tab with `rel=noopener`. Markdown posts can embed Svelte components.

**Everything is prerendered** (`export const prerender = true` in `src/routes/+layout.js` and each `+page.js`/`+server.js`); there is no server runtime. Dynamic behaviour lives client-side or in Netlify functions.

**Other areas:**
- `src/routes/playground/*` — standalone interactive toys (music tools using tone/tonal/vexflow, poker planning, timers, etc.) not tied to posts.
- `<html lang>`: `src/app.html` has a `%lang%` placeholder, replaced by `src/hooks.server.js` with the post's `lang` on post pages (`en` elsewhere); `src/routes/+layout.svelte` updates it after client-side navigations.
- `src/lib/stores/i18n.js` — homemade en/fr i18n via a tagged-template store (`$i18n\`key\``); add labels for both languages there.
- `lambda/src/*` — Netlify functions (separate `package.json`, bundled by esbuild): `polls`/`poll-description` (Airtable-backed safety-check poll) and `pusher-auth` (presence-channel auth for the poker planning playground). Shared CORS/JSON helpers live in `lambda/src/utils/http.js`: only allowed origins get CORS headers (lacourt.dev, the Netlify deploy previews, localhost; override with the `ALLOWED_ORIGINS` env var), and errors return a generic message. Never log the Pusher instance or raw events (they contain secrets), and keep validating inputs before they reach Airtable formulas or Pusher.
- `src/lib/components/ContactBlock.svelte` — the shared en/fr "get in touch" block that `Post.svelte` adds at the end of every post, before the Giscus comments (`#comments`); its links are counted as GoatCounter events (`contact-*`, `share-*`). Posts no longer need a hand-written sign-off.
- `src/lib/components/RelatedPosts.svelte` — the "Read next" / "À lire aussi" block of published posts (between the content and the contact block): 3 posts chosen by `getRelatedPosts` in `src/lib/posts.js` (shared tags, then category and language, archived posts last). Since the list of posts is server-only, each post gets a small prerendered JSON file (`src/routes/related/[key].json`, `/related/2019_06_16.json`) that `loadPublishedPostForSlug` fetches: inlined in the prerendered page, downloaded only on client-side navigations. Tags are what relate posts: give new posts some. Clicks are counted as a GoatCounter event (`related`).
- `static/_headers` — Netlify security headers (no CSP yet).
- Analytics: GoatCounter (cookieless, site `lacourtdev`). The script tag is in `src/app.html` and counts the first page view; client-side navigations are counted by `afterNavigate` in `src/routes/+layout.svelte`. The e2e tests always block `gc.zgo.at` and `*.goatcounter.com`; keep `src/routes/privacy-policy` in sync if the tracking changes, and allow `gc.zgo.at` + `lacourtdev.goatcounter.com` in a future CSP.
- There is no `svelte.config.js` anymore (SvelteKit 3): the SvelteKit options (adapter, mdsvex preprocessing, extensions) are passed to the `sveltekit()` plugin in `vite.config.js`, which also passes the `customElement: true` compile option to components that have `<svelte:options customElement=...>`.
- `src/lib` is imported as `#lib/...` (subpath imports declared in `package.json`), with the file extension (`#lib/posts.js`, `#lib/music.ts`).
- `patches/` — patch-package fixes for twemoji, twemoji-parser and hast-util-to-string; keep them in sync if those dependency versions change.

**Visual regression tests.** `e2e/visual.spec.ts` compares screenshots (a post's first screen, a figure, a table, a code block, the contact block, the 404 page, on desktop and on a Pixel 7) with the reference images of `e2e/__screenshots__/<project>/`. Its `visual-desktop` and `visual-mobile` projects only exist with `VISUAL=true`, so `npm test` skips them: font rendering differs from one machine to another, and the references are generated by the `visual` job of the CI in the official Playwright Docker image (its tag must match the `@playwright/test` version). After an intended visual change, push a commit whose message contains `[update-screenshots]`: that job regenerates the references and commits them to the branch; review them. Keep the screenshots away from what changes with new posts (the home page) or with time (the footer's year is masked).

**Playwright specifics.** Specs import `test`/`expect` from `e2e/fixtures.ts` (not `@playwright/test`), which also holds the shared assertions, `visit()` (navigates without waiting for the `load` event: each test has a fresh, empty HTTP cache) and `mockNetwork()` (JSON requests answer 404, Giscus is blocked, the Uptime Robot status API is mocked). `BLOCK_HOSTS='host1,*suffix'` aborts requests to those hosts, like Cypress' `blockHosts`.

Dependencies are pinned to exact versions and updated by Renovate.
